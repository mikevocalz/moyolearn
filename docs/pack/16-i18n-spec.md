# Cross-Platform i18n Spec — one catalog, two renderers, safety-gated languages
**Doc 16 · Moyo platform pack · Date:** Aug 21, 2026

## 1. Decision: `use-intl` shared core + `next-intl` on web (ADR-016)
**The spine:** [use-intl](https://next-intl.dev/docs/environments/core-library) is next-intl's framework-agnostic core — same `useTranslations` / `useFormatter` / `IntlProvider` APIs, ICU messages, ~13KB — and its docs list **React Native as a supported environment with an official Expo example**. So the monorepo gets the dream shape: shared components in `packages/app` call `useTranslations` once, and the same code renders localized on Next **and** Expo. Web adds the [next-intl](https://next-intl.dev/docs/getting-started) layer for what only web has: locale routing, Server Components, metadata.
**Why not the alternatives (honest):** [react-i18next + expo-localization is the most battle-tested RN combo](https://simplelocalize.io/blog/posts/the-most-popular-react-localization-libraries/) — but it means two libraries or a weaker Next RSC story; [Lingui](https://lingui.dev/) is excellent compile-time ICU but a bigger toolchain shift; **Paraglide has no official React Native adapter** (as of Apr 2026, per the same survey) — disqualified. use-intl wins on *one API, one catalog, one author, best-in-class App Router integration*.
**Known RN caveats, budgeted not discovered:** ICU plural/ordinal support depends on `Intl.PluralRules` availability — historically RN needed [FormatJS polyfills](https://formatjs.github.io/docs/polyfills/intl-pluralrules/) and the wiring has sharp edges ([next-intl #1649](https://github.com/amannn/next-intl/issues/1649)). The adoption PR **verifies Hermes Intl coverage on Expo SDK 57 first** and adds per-locale polyfills only if the runtime lacks them — checked against installed source, per the standing rule.

## 2. Web: `next/root-params` (Next.js ≥ 16.3)
From the post, adopted as the web wiring: the root layout moves to `app/[locale]/layout.tsx`; [`next/root-params`](https://next-intl.dev/blog/nextjs-root-params) lets any Server Component read the locale deeply (`await locale()`); `i18n/request.ts` reads it once with `hasLocale` runtime validation + `notFound()` for unknown segments; `generateStaticParams` pre-renders every locale; `setRequestLocale` and manual locale overrides get deleted. **Caveat carried into our patterns:** root params don't reach Route Handlers or Server Actions yet — exactly where our Block operations live — so **server operations always receive locale explicitly from `ctx`** (which we do anyway: locale is a property of the acting profile, §3), never from ambient request magic. The [`Locale` type augmentation](https://next-intl.dev/docs/workflows/typescript) makes `getLocale()` return the literal union — doc-10 discipline for free.

## 3. The locale model (Moyo-specific, binding)
- **Locale is per-profile, not per-device.** A guardian may run the app in Spanish while their child learns in English — or the reverse. `profile.locale` (UI) travels in `ctx`; device locale via [expo-localization](https://docs.expo.dev/versions/latest/sdk/localization/) and the `[locale]` segment are only the *defaults* for signed-out/new states.
- **Two locale axes, registry-gated:** `uiLocales` (the strings are translated) and `aiTutorLocales` (**every Safety Plane layer has passed evals in that language**). They are independent registry entries. **A language ships for learner AI only when L1–L5 classifiers and the red-team suite are validated in it — fail-closed applies per-locale.** Until then the UI can be Spanish while tutoring runs in cleared languages, with honest copy ("Natalie is still learning Spanish") and guardian choice. Safety coverage, not translation completeness, is the gate — this is the rule a generic i18n guide would never give you and the one that matters most here.
- **Rollout:** `en` → `es` (the largest US family segment) → then `sw` — Swahili as the brand-coherent heritage statement — and `fr`. Ops-cloud locales may lag family locales; both lists live in the registry with the paywall/nav copy.

## 4. Design & content rules
- **Expansion budgets now, not later:** es/de run ~+30% longer — doc-08 layouts are audited with a **pseudo-locale** (elongated, accented) screenshot pass in CI, same harness as the target-size audit.
- **RTL readiness (Phase with `ar`):** RN [`I18nManager`](https://reactnative.dev/docs/i18nmanager) + logical start/end styles from day one so RTL is a flip, not a rewrite. Design ruling: directional UI (chevrons, back, progress) mirrors; **the ink slab shadow does not** — it's the system's lighting constant, not a reading-direction cue.
- **Reading-band × language:** the doc-08 reading ramp applies per language — child-facing strings are translated to the *band's* reading level, which is why **child-facing catalogs require human review; machine-only translation is banned for learner surfaces** (an AI first pass is fine; a human signs off). Curriculum/AI content localization is a separate pipeline from UI catalogs entirely.
- **Formatting:** all dates/numbers/currency through `useFormatter` — never hand-rolled; currency follows the business's locale on ops surfaces; times respect the scheduling timezone rules (doc 03).

## 5. Monorepo architecture
`packages/i18n`: message catalogs (`en.json` source of truth, namespaced by screen-brief ID — `S1`, `ops.schedule`, `paywall`), the typed `Locale`/`Messages` augmentation, shared config, and the registry's two locale lists. Consumed by `apps/web` (next-intl + root-params) and `apps/mobile` (use-intl `IntlProvider` + expo-localization default + polyfill shim if the Hermes audit demands it). **Enforcement (doc 11 §6 extension):** a lint rule bans raw string literals in shared/learner JSX — every user-visible string goes through `t()` — and message keys typecheck via the augmentation, so a missing translation is a build error, not a runtime blank.
