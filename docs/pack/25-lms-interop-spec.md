# LMS Interop — two lanes in, one gate out: LTI Advantage + the Content Connector
**Doc 25 · Moyo platform pack · Date:** Aug 21, 2026
**Verdict on the advisor doc:** adopt the architecture — it's the strongest one yet. The two-lane insight (LTI carries identity/roster/deep-links/grades; a separate Content Connector carries what the AI actually reads) is correct and most teams miss it, shipping LTI launch and then wondering why their tutor is context-blind. Adopted with the corrections below, which mostly make its softest parts structural.

---

## 1. The two lanes (adopted)
- **Lane 1 — LTI 1.3 / LTI Advantage** ([LTI 1.3](https://www.imsglobal.org/spec/lti/v1p3), [AGS](https://www.imsglobal.org/spec/lti-ags/v2p0), [NRPS](https://www.imsglobal.org/spec/lti-nrps/v2p0), [Deep Linking](https://www.imsglobal.org/spec/lti-dl/v2p0)): secure launch context (student/teacher/course/resource/school/district), roster/roles, teacher deep-linking of Moyo activities into Canvas/Schoology/etc., grade passback. No second login. This extends doc 13 §11 — LTI was already the Phase-4 institution channel; this doc deepens what flows through it.
- **Lane 2 — the LMS Content Connector** (provider APIs; [Canvas API](https://canvas.instructure.com/doc/api/) first — richest and best-documented): assignments, modules, pages, files, rubrics, syllabus, announcements → sync worker → normalize → Payload metadata → chunk/embed → permission-filtered retrieval → tutor context. **Never query the LMS live per student question** — sync-then-retrieve wins on latency, auditing, permission enforcement, and cost. [OneRoster 1.2](https://www.imsglobal.org/activity/onerosterlis) stays the roster lane, with the advisor's identity-matching pipeline adopted: match on district-provided identifiers, attach enrollments to existing canonical students, and **ambiguous matches go to a human review queue — never auto-merge** (docs 06/11).
- **Normalized model + mapping layer (adopted):** provider-agnostic `Course/ClassSection/Assignment/Submission/Grade/Enrollment` internals; `ExternalIdentity` records so one student exists across Canvas/OneRoster/Classroom without becoming three students; external IDs never become our IDs. Connections are **scope-aware** (a district can run Canvas in high schools and Schoology in middle schools); the advisor's Payload collection list (`lmsConnections`, `lmsResources`, `lmsAssignments`, `lmsMappings`, `lmsSyncRuns`, `ltiDeployments`, …) is adopted as the schema skeleton. Registry-gated, Institution tier.

## 2. The corrections — where soft becomes structural
1. **The answer-key wall is an index boundary, not a filter.** The advisor's `visibility` + `aiUsage` enums are adopted (`disabled | teacherOnly | studentTutor | assessmentGrading`, default **`disabled`** — teachers opt content *in* via the source-picker UI, which is adopted as drawn). The hardening: the student-tutor retrieval index is **built exclusively from `aiUsage: 'studentTutor'` resources — answer keys and teacher-only material never enter that index at all**, so no retrieval bug can leak them; a CI check (the doc-13 edu-import pattern) fails any build where the student index builder can read anything else. Teacher-AI evaluation runs against a separate index in a separate gateway lane — the AI can grade against the key without the tutoring context ever containing it.
2. **One session bootstrap, not two.** The advisor's `TutorGroundingContext` merges *into* the doc-19 learner brief — one compiled object per session: assignment + teacher instructions + rubric + approved sources + mastery state. Its `answerPolicy` field exists but is **not configurable downward for learner sessions**: `guided-only` is the doc-18 pedagogy contract, not a district setting. The layered retrieval levels (session → lesson → course → student → institution) are adopted as the retrieval planner's ordering.
3. **AI scores are non-authoritative by default — adopted fully.** The `LTIGradePassback` object ships with its `source` enum and progress states; mastery % and session-completion push only where teacher-enabled; teacher-reviewed grades are the only default-authoritative lane. This is doc 19 §4's AGS passback, now with its write model.
4. **The sync-direction table is policy:** rosters LMS→platform; assignments and grades bidirectional (teacher-controlled); tutor sessions platform→LMS; **learning profile, guardian relationships, and billing are platform-owned — no LMS write path exists to them**, which is the doc-13/23 wall restated at the sync layer.
5. **Embeddings follow doc 19 §5.5:** LMS content is *content* — embed it. Chunks carry the resource's visibility/`aiUsage`, and retrieval filters by permission **before** similarity, never after. The per-class "Knowledge Space" (the advisor's NotebookLM instinct) is doc 18's curriculum-RAG layer unified: LMS content, teacher uploads, and licensed materials in one provider-agnostic source space, routed to whichever model the ADR-018 routing table serves that cell.
6. **Sequencing:** launch + AGS first (the procurement door), Canvas content connector second, Schoology/Classroom/Moodle staged behind the same normalized interface; [1EdTech LTI Advantage certification](https://site.imsglobal.org/certifications) pursued once launch+AGS are solid — it's a named line in district RFPs.
