# SPEC — Embodied Natalie: the 3D tutor avatar on React Native WebGPU
**Doc 22 · Moyo platform pack · Date:** Aug 21, 2026
**What this is:** the binding spec for porting the working browser avatar (`gnm-avatar`, 27 commits, Phases 1–9 complete) onto the Moyo app as a real-time tutor presence. §3–§8 are **decisions**, not options — they were made with the reference implementation open and every three.js API verified against the r185 source tree. The agent's job in §10 is to implement and stress-test them.

This doc fills the mount point doc 01 reserved: *"`TutorStage` (2D avatar v1; mount point contracts sized for 3D/XR later)"* and *"the tutor-presence avatar — one continuous identity from tab-bar icon → session stage → (later) AR/XR embodiment."* It is the 3D stage. It supersedes nothing; it inherits doc 07 (Safety Plane), doc 15 (Natalie's voice + the Margelo prior art), doc 17 (motion), doc 20 (**zero avatar bytes in the binary**), and doc 08 (age bands, reduced motion).

## §3 · The decision (binding)

**We port the renderer, not the app.** The browser app is the reference; the target is a `packages/avatar` module consumed by `TutorStage` in `apps/mobile` and `apps/web`.

**Runtime:** [`react-native-webgpu`](https://github.com/wcandillon/react-native-webgpu) (Dawn-backed, `dawn: chrome-m150`) with three.js's `WebGPURenderer`. **Pinned to three `0.185.1`** (§6). Verified against the working harness at `react-native-webgpu-main2/apps/example/src/ThreeJS` — eight three.js examples including a skinned animated GLTF (`Backdrop.tsx`), IBL + HDR (`Helmet.tsx`), TSL post-processing (`PostProcessing.tsx`), and skeleton retargeting (`Retargeting.tsx`). That harness is the porting reference; read it before writing a line.

**Three non-negotiables, stated up front:**

1. **There is no incremental path from the WebGL renderer.** `onBeforeCompile` does not exist on `NodeMaterial` and `THREE.ShaderChunk` is exported only from the WebGL entry point (`src/Three.js`), not from `three/webgpu`. Every one of the six GLSL-injection sites is a rewrite against node properties or the lighting-model hooks. Budget for that honestly; do not plan a "shim".
2. **Zero avatar bytes in the app binary** (doc 20, carried from doc 18). The 34.9 MB head container, the body glb, and every baked JSON/bin ship from the CDN behind the capability manager's cache. This is not a size optimisation — it is the same rule that keeps model weights out of the binary, and it applies identically here.
3. **The avatar is a learner surface.** Everything in doc 07 §3 and doc 05's visibility matrix applies to it: no price, paywall, or upgrade prompt may ever render on the stage; the fail-closed state has an avatar behaviour, not an error screen; the companionship firewall governs the *body* as well as the words (§7).

**What is deliberately cut from v1:** the mic listener (`src/idle/listen.ts`) — Natalie's turn-taking comes from the gateway stream, not from an always-on microphone at a child; the `/body` QA page; the orphaned `arkit-morphs.bin` and the assigned-but-never-attached `uv.bin` head UVs.

### The audio seam that does remain

The clock is shared; three things around it are not, and pretending otherwise is how lip sync ends up 200 ms late on someone's headphones.

- **`onPositionChanged` / `onPositionChangedInterval` and `getLatency()` are mobile-only** — they do not exist on the web `AudioBufferSourceNode`. Poll `ctx.currentTime` per frame as the primary (it is the better primitive for a per-frame viseme sample anyway) and treat the native position callback as a cross-check, never as the source of truth.
- **Output latency is not in `currentTime`.** `currentTime` is the graph clock, not the speaker clock, and `getLatency()` returns 0 unless pitch correction is on — so it will not report the 150–300 ms a Bluetooth route adds. If the mouth needs a per-route offset, `AudioManager.addSystemEventListener('routeChange')` is the hook. Measure this on wired, speaker, and Bluetooth before deciding it doesn't matter.
- **iOS audio-session configuration is real work, and it fails loudly.** `setAudioSessionOptions({ iosCategory, iosMode, iosOptions })` must be set before any `AudioContext` exists, and an invalid combination throws `SessionActivationError` and produces **total silence** — a mute avatar with no error at a child. Wire the interruption observers (`interruption`, `routeChange`) at the same time: a phone call mid-lesson must pause the tutor, not desync her.
- **Decoding is whole-buffer.** `decodeAudioData` resolves only after the full MP3 decodes, so the reference's `ONSET_LEAD_MS` pre-roll stays load-bearing — schedule the onset after the decode resolves, exactly as the reference does.
- **Web `AnalyserNode` property assignment appears broken** in 0.13.3 (`fftSize` and friends are plain constructor-snapshotted fields with no setters on the web wrapper). Only relevant if an amplitude-driven fallback is ever built; pass options to the constructor rather than assigning, and verify first.

Expo note: the package ships a config plugin and **does not work in Expo Go** — it needs a development build, along with `iosBackgroundMode` / Android foreground-service options if the tutor is ever to keep talking off-screen.

## §6 · Device tiers and budgets (binding)

The reference already has the vocabulary: `?quality=low|medium|high` for hair/wardrobe, `?tm=` for tone mapping. Formalise it as a discriminated union in `packages/avatar/src/tiers.ts`.

| Tier | Devices | Head evaluation | Post chain | Hair/wardrobe | Frame budget |
|---|---|---|---|---|---|
| **`presence-2d`** | no hardware adapter; software fallback; Android emulators | none | none | none | — |
| **`phone`** | modern phones | CPU (`computeVertices`), evaluate on dirty only | scene pass only, MSAA off, bloom off, AO off | `low` | 16.7 ms at native res, **DPR capped at 2** |
| **`tablet`** | tablets, macOS, desktop web | compute path (row 14) if `adapter.limits` allow, else CPU | `pass({samples:4})` + `bloom` | `medium` | 16.7 ms |
| **`studio`** | desktop web, visionOS | compute | full: `pass` + `ao(GTAO)` + `bloom` | `high` | 16.7 ms |

**Tier selection is measured, not guessed.** On mount: `navigator.gpu.requestAdapter()` → check whether the adapter is a software fallback (see below) → read `adapter.limits` → pick a tier → run 60 frames → demote a tier if the EMA frame time misses budget. The reference already exposes `stage.stats` (`frameMs` EMA + `drawCalls` across all passes with `renderer.info.autoReset` disabled) — port it and make the demotion automatic. **A fallback adapter is an immediate hard fall to `presence-2d`.**

**Platform reality, verified against the harness:**

The upside of moving is real (`ssao()`, a cheaper AO node, arrives in r186), so this is a scheduled decision, not a freeze.

**The 34.9 MB question.** It is the whole ballgame on a phone plan, and it is why row 3 of §3 exists.
1. **First contentful presence must never wait on it.** `TutorStage` mounts the 2D presence mark (already the tab icon) and streams the 3D stage in behind it. The existing `fetchWithProgress` reader gives real progress.
2. **Download once, cache forever.** The container is content-addressed and immutable (the web build already serves it `max-age=31536000, immutable`); the capability manager owns eviction.
3. **Rebake it — and the number is much better than a trim.** *(Measured against the shipped `arkit-map.json`, Aug 21; this supersedes an earlier, wrong claim in this section that the map touched only a few components.)*

   The ARKit map is **dense**: all 383 GNM expression components carry non-trivial coefficients, and the top 128 capture only ~54 % of the coefficient energy. So component pruning does **not** work — which is the good news, because it forces the right answer instead.

   `face-bus.ts` is the single face writer and it *only* ever writes through the map: 19 named ARKit weights in, one `setExpression` out. The runtime therefore never needs a 383-dimensional basis — it needs the **precomposed product**. The composition is linear and therefore exact:

   ```
   exprSum = Σ_k expr_k · basis_k ,  expr = Mᵀw          (w = the 19 ARKit weights)
           = Σ_i w_i · (Σ_k M[i][k] · basis_k)
           = Σ_i w_i · arkitBasis_i                       ← bake THIS, 19 channels
   ```

   And the identity is **frozen** — one baked `identity.json`, sha-256-gated, never varied at runtime. So the identity basis does not ship either: pre-apply it to the template (and the joint-identity basis to the template joints) and ship the resulting bind pose.

   **Built and measured, not proposed.** `tools/bake_runtime_container.py` emits the runtime container; `tools/verify_runtime_bake.ts` runs the shipped container *and* the rebaked one through the real `GNMHeadModel` and diffs world-space vertices — including under eye-gaze FK, because a bake that only preserved the bind pose would pass a static check and fail the moment the head moves.

   | | Shipped | Rebaked (int8) | Rebaked (float32) |
   |---|---|---|---|
   | expression basis | 20.48 MB (383 × int8) | **1.02 MB** (19 × int8) | 4.06 MB (19 × f32) |
   | identity basis | 13.53 MB (253 × int8) | **0 — folded into the template** | 0 |
   | **container** | **34.94 MB** | **1.93 MB — 18.1×** | 4.97 MB — 7.0× |
   | max vertex error, realistic poses | — | **0.06 mm** | 0.0001 mm |
   | max vertex error, all 19 channels at 1.0 | — | 0.33 mm | 0.0001 mm |
   | neutral pose | — | **0.0000 mm (bit-exact)** | bit-exact |

   The head is 341 mm tall, so int8's worst realistic error is **0.018 % of head height** and the pathological all-channels case is 0.098 %. Neutral is bit-exact because the identity fold is exact arithmetic, not an approximation.

   **Decision: ship int8, 1.93 MB.** It holds the existing quantisation contract, so `GNMHeadModel` and `parseContainer` read it with no code change at all — `identityDim` becomes 0 and `expressionDim` becomes 19, and everything else is data. `--basis-dtype float32` is one flag away if a golden diff ever disagrees.

   There is a second win riding along: the runtime writes the 19 ARKit weights **straight in** as the expression vector, which deletes a 19 × 383 matrix multiply from every speech frame. `ArkitMapper` stays in the package for the authoring path, but the shipping face bus does not call it.

   **What it costs:** runtime identity changes (Editor presets, the tuning pass) and raw 383-vector `setExpression` — both authoring affordances, both of which stay available in `gnm-avatar`, which keeps the full container as the authoring asset. If a future viseme set needs ARKit channels beyond these 19, re-bake; the bake is cheap and the map is the input.

   **The download is no longer the hardest constraint in this document.** 34.94 MB was a Wi-Fi-gated, progress-barred, capability-manager-cached problem; 1.93 MB is smaller than a single photo in the app and changes what §6's first-paint strategy has to defend against.
4. **Wi-Fi gating is now a judgement call, not a requirement.** At 34.94 MB it was mandatory. At 1.93 MB it is comparable to a couple of photos, so the default can be "just fetch it" — but keep the metered-connection check for the tier that streams 8K textures later, and never let a first launch on cellular surprise a family.

## §7 · The child-safety and accessibility boundary

The avatar is the most emotionally salient surface in the product. Every rule below is testable and belongs in the red-team suite alongside the doc 07 text checks.

- **The Safety Plane owns the performance, not just the words.** Visemes, emotion category, and the EMAGE gesture track are *outputs of the learner AI turn* and travel with it through the gateway (doc 12 §5). A feature **never** calls a model, a TTS provider, or an animation service directly. When any safety layer is unavailable, the fail-closed rule applies to the body too: Natalie's stage goes to a **calm, authored idle** with the guardian-visible "taking a break" status — never a frozen T-pose, never an error screen, never a mesh that vanishes mid-sentence.
- **The companionship firewall extends to the body.** Doc 02: *"Natalie 'helps you learn it by heart'; she never 'loves you.'"* The gesture vocabulary is bound by the same line — no simulated affection, no reaching toward the camera, no leaning-in intimacy beats, no eye contact held past a conversational norm. The idle engine's backchannel nods and pre-speech anticipation are **attention** cues, which is the point; anything that reads as **attachment** is out. Enumerate the permitted gesture set explicitly and gate the EMAGE output against it.
- **No paywall, price, or upgrade prompt renders on the stage. Ever.** (doc 05 visibility matrix; repo law.) There is no "unlock premium Natalie" moment in front of a child.
- **No engagement-pressure mechanics.** No idle behaviour that reads as sulking, waiting, or disappointment; no attention-getting motion after inactivity; no late-night presence. Doc 04's rule — *"Celebration is warm, never manipulative"* — governs the body language.
- **Reduced motion is a first-class render mode, not a CSS afterthought.** Doc 01 says explicitly *"reduced-motion honored (tutor avatar included)."* The idle engine (breath, sway, drift, saccades, hair secondary motion, camera float) has a **static mode**: speech-driven mouth and minimal blink only, everything else pinned. This is vestibular accessibility, and on a headset it is safety, not preference.

  ✅ **Built** as `src/reduced-motion.ts`, and building it surfaced the gap this bullet was written to prevent. Reduced motion existed as **three independent booleans** — `faceBus.setReducedMotion`, the hair material's `motionScale` argument, and nothing at all for camera float. Each worked; nothing connected them, so honouring the setting meant remembering three call sites, and the fourth animated surface someone added would ship unwired because nothing would fail when they forgot. That is exactly the "afterthought" failure, arrived at by accretion rather than by neglect.

  The fix is one `MotionMode` → one `MotionPolicy` → an `ANIMATED_SURFACES` registry naming every moving thing, the policy field that governs it, and the consumer that reads it. `assertMotionPolicyComplete()` fails the build when an animation has no governing field or no named consumer, so forgetting is now a red test rather than a silent regression.

  Two behaviours are deliberate and inverted from the naive implementation. **XR is a floor, not a default**: a user may ask for less motion anywhere, but may only override back to full where the consequence is aesthetic — which is not a headset, so a system-level reduce request in XR is non-overridable. And **the mouth and the blink are never scaled, in either mode**: a tutor whose lips do not move is broken rather than restful, and a face that never blinks is unsettling rather than calm. Reduced motion removes vestibular load, not the signs of life.
- **No camera. No microphone in v1.** The reference's mic listener is cut (§3). If turn-taking later wants audio-in, it enters through a consent flow written against doc 07's ladder, not through a renderer feature flag.
- **The renderer holds no learner PII.** Nothing identifying is ever textured, labelled, or logged on the stage. Doc 06's avatar *picker* (a child choosing a picture to log in with) is a different thing entirely and stays that way.
- **Age-band framing.** Doc 08's bands govern the stage's own controls: any interactive affordance on or around the avatar takes the age-band target token (72 pt / ~2 cm for the young band), not a 44 pt default.

## §8 · Determinism and the golden-image gate

Do not lose this on the way across. The reference's harness — `?seed=N&fixedDt=1&stopAt=240`, 7 cameras, `window.avatar.frameCount`, pixelmatch at 0.4 % — is what made nine phases of shading work reviewable instead of arguable.

**Port it, and make it better on this platform.** `react-native-webgpu` ships **`GPUOffscreenCanvas`** (`new GPUOffscreenCanvas(w, h)`, `.getContext('webgpu')`, async `.getImageData()` returning `{data, width, height, format}`), which means the avatar can render **headless on device or in CI and read the pixels back** — no Chrome dependency, no `puppeteer-core`, no `/Applications/Google Chrome.app` hard-coded path. That is a strictly better harness than the browser one it replaces.

Gates, added to the standing per-PR set in `00-START-HERE.md`:
- `turbo typecheck` green from a cold cache.
- Golden set green at ≤ 0.4 % pixel diff on **every** tier that ships, not just the top one.
- Frame budget met on the tier's reference device (`stats.frameMs` EMA over 240 fixed-dt frames).
- **Re-approval is a reviewed act.** Any three.js bump, any lighting-model touch, any AO retune re-approves goldens *with the diff images in the PR*. Silent `--update` is the failure mode this whole harness exists to prevent.
- Reduced-motion mode has its own goldens (it must be *still*, and a diff proves it).

## §9 · Trade-offs (so nobody relitigates silently)

| Decision | Traded away | Why it's right | Revisit when |
|---|---|---|---|
| `WebGPURenderer` + TSL over a WebGL RN renderer | a mechanical port; all six shader patches are rewrites | WebGL on RN is a dead end for this workload — no compute, no modern node materials, and the platform is moving | never |
| three pinned at `0.185.1`, bumped only by reviewed PR | riding upstream fixes for free | the reference renderer already runs it, so the port carries no version drift; r186 breaks §4 rows 1, 10, 11 | r186's `ssao()` node is worth the retune |
| `PCFShadowMap` over `PCFSoftShadowMap` | a little softness on r185 | the only value that survives r186 and matches WebGL | r186 lands and the diff is measured |
| GTAO via `builtinAOContext` over an `SSAOPass` look-alike | 1:1 parity with the reference frames | it is the sanctioned node and physically better placed; parity was never the goal, quality was | a cheaper `ssao()` node (r186) beats it on mobile |
| CPU head evaluation on the phone tier | GPU headroom | it is proven, dependency-free code, and the compute path has a real `maxStorageBuffersPerShaderStage` risk | `adapter.limits` on the real device fleet say otherwise |
| Baked lash texture over a canvas polyfill | runtime flexibility nobody uses | deterministic, smaller, and removes a DOM dependency from a native renderer | never |
| Avatar assets on the CDN, never in the binary | first-run instant 3D | doc 20's law, and a 35 MB binary bump for a Phase-3 surface is indefensible | never |
| Reduced motion as a render mode, not a toggle | one code path | vestibular accessibility is a floor, and on XR it is safety | never |
| One shared audio implementation (`react-native-audio-api`) over a per-platform clock | native-only position/latency APIs on web | it is Web Audio on all three targets — web delegates to the browser engine — so the clock, the decode, and the scheduling are one code path, and it was already in the catalog | the remaining mobile-only surface (position callback, `getLatency`) becomes load-bearing on web |
| Mic cut from v1 | natural barge-in turn-taking | an always-on microphone at a child needs a consent story, not a feature flag | doc 07 has one, written and reviewed |

5. **The offscreen golden harness** (§8) — ✅ **built, and it is the remaining critical path.** Landed as `src/testing/{golden,png,pixel-diff}.ts` + `tools/golden-compare.ts`, 22 tests. The design decision worth knowing: **the device captures, the host compares.** `golden.ts` runs on device and imports nothing Hermes lacks — it owns the deterministic setup, the camera set and the capture loop, and hands back raw RGBA. The PNG codec and the perceptual diff use `node:zlib` and run host-side in CI. Shipping an inflate implementation into a renderer package to service a test would be the tail wagging the dog.

   The diff is `pixelmatch`'s algorithm (Yee's YIQ metric with the antialiasing heuristic) reimplemented rather than depended on. **AA exclusion matters more here than in a typical snapshot suite**: the groom is 250 braids of one-pixel ribbons and the lashes are alpha cutouts, so a half-pixel camera nudge lights up thousands of edge pixels that no reviewer would call a regression. Five reproducibility invariants are asserted rather than hoped for — fixed timestep, fixed seed, damping off, DPR pinned to 1, and warm-up frames rendered at `dt = 0` before the clock starts (pipeline compilation and PMREM live there). `assertCaptureInvariants()` reports all violations at once, because each one produces a golden that passes on the machine that made it and fails everywhere else, which reads as flakiness and gets the gate switched off rather than the setup fixed.

7. **The gesture-vocabulary gate** (§7) — ✅ **done** as `src/safety/gesture-gate.ts`, 21 red-team cases written as attacks rather than as coverage.

   §7 says *"enumerate the permitted gesture set explicitly and gate the EMAGE output against it"*, and those turn out to be **two mechanisms**, because EMAGE does not emit named gestures — it emits a 30 fps stream of SMPL-X joint rotations, and a pose stream cannot be name-checked. So: `PERMITTED_GESTURES` is the enumerated vocabulary governing what may be *authored* (nine entries, each stating which conversational function it serves), `FORBIDDEN_GESTURES` names what is out **with the doc line each one violates cited**, and `gateGestureTrack()` is a structural gate on the stream that caps the joints which actually *produce* the forbidden reads: cumulative torso pitch makes a lean-in, shoulder flexion makes a reach, sustained head-toward-camera makes a stare. Capping those caps the behaviour regardless of what the model thought it was generating.

   Three properties are worth stating because they are the ones that make it a gate rather than a decoration. **Rejection is whole-track** — splicing out a bad window produces a pose discontinuity mid-sentence, which reads as a glitch and draws exactly the attention the rejection was avoiding. **The fallback is `CALM_IDLE`**, breath and blink only, matching §7's explicit failure mode: never a frozen T-pose, never an error screen, never a vanishing mesh; a child should read "she has gone quiet", which is a thing people do. And the gate **must not over-reject** — a tutor who never meets your eye is its own problem, so mutual gaze that is made and broken passes; only a *held* stare fails. There is one honest caveat, flagged on the export and checked by `assertRigSemantics()`: the SMPL-X pitch axis and sign must be verified against the real rig, because a sign flip would make the gate PASS precisely the tracks it exists to reject — which is strictly worse than no gate, since it would provide false assurance in review.

   `assertNoEngagementPressure()` covers the other half of §7 — no attention-getting motion after inactivity, no sulking or waiting states, no late-night presence. These are the mechanics a growth team reaches for by reflex, so the value of asserting them is that adding one becomes a failing test with a doc citation attached rather than a plausible-sounding ticket.

Row 13's blocker is retired outright; row 14's risk is downgraded because the rebake cut the kernel from ~7 storage buffers to 4, and the gate now fails closed to the proven CPU path with a message that names the fix. **158 tests green**, both kernel sub-projects and the package typecheck clean against real `@types/three` 0.185.4.
8. **`TutorStage` wired** to swap 2D presence ↔ 3D stage — ✅ **done** as `src/tutor-stage.ts`, a renderer-free state machine on the contract doc 01 reserved and inside the states doc 23 drew. It enforces one rule: *2D is shown from the first frame and is never taken away until 3D can actually draw a face* — not "assets downloaded", not "renderer initialised", but a real rendered frame. Four consequences are encoded rather than documented: the swap **waits out an utterance** (a face changing identity mid-sentence is uncanny in a way a delay is not); it **will not swap inside the first ~900 ms** (a swap that fast reads as a glitch, because the child never registered the first face); demotion is **irreversible**, matching `tiers.ts`, because flapping between two tutors is worse than either alone; and a download failure resolves to **2D with a telemetry reason, never an error surface** — doc 23's union has no `error` kind and this respects it. The stage keeps rendering off-screen during `pending-swap` so the handover is not a cold first frame.
9. Standing gates: no invented APIs — **cite file + symbol for every seam**, and re-verify anything in §11 against the pinned three version rather than against this document. — ✅ **now mechanised.** `tools/verify_doc_claims.mjs` extracts every backticked identifier in this document and resolves it against the actual runtime exports of `three`, `three/webgpu`, `three/tsl` and the four `three/addons` paths §4 cites, plus `@types/three`'s declarations (for type-only and property-only claims like `LightingModelDirectInput` and `colorNode`) and this package's own barrels (loaded, not listed — a hand-maintained allowlist in an auditing tool goes stale and then teaches the reader to skim). ## §11 · Open questions — verify on hardware, do not assume

The three version is **not** one of these: it is pinned at `0.185.1` (§6). Items 1 and 4 double as the re-verification checklist for the eventual r186 bump.

1. **Visual parity of the ported lighting model.** The API surface is verified; the output is not. r185 vs r186 `PhysicalLightingModel.direct()` differ materially. Needs an A/B render against the existing `RE_Direct_Physical` patch.
2. **`maxStorageBuffersPerShaderStage` on the real device fleet.** Spec default is 8. **Now measured on our side: the kernel binds 4** (template, expression basis, skinning weights, output) against a rebaked container, because the identity basis is gone and the joint transforms ride in uniform buffers. The earlier ~7 was for a raw container and is what `canUseComputeHead()` still reports for one. That is a real margin rather than a coin flip, but it is a margin against a *number*, not against hardware: still query `adapter.limits` on Apple/Adreno/Mali before turning the compute tier on, and note the gate already fails closed if it is wrong.
3. **Half-float LTC quality** for `RectAreaLight` on mobile (`float32Filterable` is likely absent) — the fallback is automatic, its look is unmeasured.
4. **Whether r186's "`PCFShadowMap` is now soft as well" matches the old `PCFSoftShadowMap`.** Unread PR diff.
5. **GTAO-vs-`SSAOPass` magnitude.** Known to differ architecturally; the size of the retune is unmeasured.
6. **Whether `computeSkinning` composes with a PCA/morph blend.** It reads position/skinIndex/skinWeight/bind matrices only; the basis evaluation must be composed *before* the skinning step. Untested.
7. **`AudioContext.currentTime` resolution is undocumented.** Nothing states whether it advances per render quantum (128 frames ≈ 2.67 ms at 48 kHz), per system callback, or interpolated. Measure it: read it in a tight frame loop and log the deltas. Coarse steps mean the viseme sample judders and wants interpolation against a monotonic wall clock anchored to `currentTime`.
8. **Whether the mouth needs a per-route latency offset.** `currentTime` is the graph clock, not the speaker clock, and `getLatency()` reports 0 without pitch correction — so a Bluetooth route's 150–300 ms is invisible to it. Test wired, speaker, and Bluetooth.
9. **Clock skew between the JS thread and the audio thread under renderer load.** Undocumented, and the library's own issue #812 suggests no published guidance. This is the risk specific to *this* port: a 3D renderer pegging the JS thread while `ctx.currentTime` is read every frame. Test with the renderer running, not in isolation.
11. **Where does the fallback-adapter flag live now?** WebGPU moved `isFallbackAdapter` off `GPUAdapter` and onto `adapter.info` during standardisation, and no WebGPU adapter was reachable here to check. `src/tiers.ts` is unaffected — it takes an `AdapterFacts` boolean — but whoever wires the app must read the right property, and reading a missing one yields `undefined`, which is falsy, which silently means "not a fallback". That is the wrong direction to fail in: a software adapter would be promoted to a 3D tier rather than dropped to `presence-2d`.

12. **Do shadows render at all on the WebGPU path?** The shader probe cannot answer it — no shadow appears on its WebGL2 fallback even for a stock directional light and a stock receiver, so the backend, not the stage, is the likely reason. First thing to check on real hardware, because §4 row 10's whole argument (`PCFShadowMap` over `PCFSoftShadowMap`) presumes shadows work.

13. **`renderer.info.render.drawCalls` reads 1 through `RenderPipeline`.** Observed on the WebGL2 backend for a scene with two meshes, a shadow pass and bloom — so `Stage.stats.drawCalls` is under-reporting by a lot. Confirm on the WebGPU backend before anyone builds a budget check on it; `frameMs` is unaffected and remains the demotion input.

14. **Thermal behaviour over a 20-minute tutoring session** on a phone. Frame budget is a ceiling; sustained thermal throttling is the real constraint and nothing in the reference measures it.
