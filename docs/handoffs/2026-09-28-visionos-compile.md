### The autolinking exclusions

`apps/mobile/react-native.config.js`, gated on `MOYO_VISIONOS_BUILD=1`, drops
four native dependencies from visionOS autolinking. iOS and Android keep all
four:

| package | why |
|---|---|
| `react-native-executorch` | published XCFramework has no xros slice |
| `react-native-pulsar` | UIKit feedback generators unavailable on visionOS |
| `react-native-keyboard-controller` | input-accessory APIs unavailable |
| `react-native-webgpu` | **added this session** |

WebGPU was the last link failure: `ld: library 'webgpu_dawn' not found`.
`node_modules/react-native-webgpu/libs/apple/libwebgpu_dawn.xcframework` ships
`macos-arm64_x86_64`, `ios-arm64_x86_64-simulator` and `ios-arm64` — no xros.
It is a prebuilt binary, so there is nothing to patch. Producing an xros slice
means building Dawn for visionOS, which nobody has done here.

`patches/react-native-webgpu@0.10.2.patch` is now dead: its entire body is
`#if TARGET_OS_VISION`, so with the pod unlinked it changes nothing on any
platform. It also blocks the calling thread on
`dispatch_semaphore_wait(..., DISPATCH_TIME_FOREVER)`. Remove it and regenerate
the lockfile — it was left in place only to avoid a `pnpm install` during a
concurrent build.

### `hearts-gpu.visionos.tsx` — a boot crash, not a nicety

This one matters. The chain is eager and unguarded:

```
apps/mobile/app/_layout.tsx:27        import { MoyoSplash } from "../components/splash/MoyoSplash"
  → components/splash/MoyoSplash.tsx:42   import { HeartField } from './hearts-gpu'
    → components/splash/hearts-gpu.tsx:37   import { Canvas } from 'react-native-webgpu'
```

`<MoyoSplash />` is mounted unconditionally at `_layout.tsx:181`. The WebGPU
entry calls `TurboModuleRegistry.getEnforcing("WebGPUModule")` and then
`install()` at module scope, so with the pod unlinked the app dies on the first
screen a child ever sees. The `.visionos.tsx` sibling returns `null`; the splash
keeps its lockup, cascade and tagline and loses only the particles.

Three other chains reach WebGPU and were deliberately left alone, all lazy:
the Natalie avatar behind `NATIVE_3D_ENABLED`
(`packages/app/features/tutor/natalie-preload.ts:24-27` — nothing in the repo
sets `EXPO_PUBLIC_NATIVE_3D`), and two `moyo://` deep-link-only harness routes
(`app/native-3d-smoke.tsx`, `app/natalie-3d.tsx`). They have no tab, link or
menu entry and are meant to fail loudly.

`three/webgpu` and `react-native-redraw` are red herrings — `metro.config.js:59-88`
collapses every `three` specifier onto `three.webgpu.js`, which wants only
`navigator.gpu`.

### `KeyboardProvider.tsx` — a regression `5ce3dff3` introduced

`5ce3dff3` replaced `_layout.tsx`'s direct `react-native-keyboard-controller`
import with a local `KeyboardProvider` that had only `.native.tsx` and
`.visionos.tsx` siblings and no base file. Metro resolves that; `tsc` and web do
not. It broke the workspace typecheck:

```
app/_layout.tsx(18,34): error TS2307: Cannot find module '../components/KeyboardProvider'
```

`KeyboardProvider.native.tsx` is renamed to `KeyboardProvider.tsx`, which
restores iOS, Android and web to the pre-change import and gives `tsc` something
to resolve. `npx tsc --noEmit -p apps/mobile/tsconfig.json` then exits 0 clean.

### `prepare-visionos.mjs` — an unrecoverable cache state

`visionos:prepare` failed on a cache that could never recover: an interrupted
checkout had written the full source tree to
`.cache/visionos/virocore` while leaving `.git/index` absent, so `git ls-files`
returned 0 and every later run died on *"The following untracked working tree
files would be overwritten by checkout"*.

The fix empties the clone (skipping `.git`) and deletes `.git/index` before
`git checkout --detach FETCH_HEAD`. The index deletion is the non-obvious half
and was tested rather than assumed: **wiping only the files makes git read them
as local deletions, so the checkout records the deletions and exits 0 with an
empty tree.** `git read-tree --empty` fails the same way. No `git clean`, no
`reset --hard` (CLAUDE.md bans both); deletions are addressed off the absolute
`core` path; `.git/objects` survives so the fetch stays a no-op.

Verified by two consecutive runs from deliberately dirty states, the second
starting from 7,703 dirty entries. Both completed checkout →
`build_visionos.sh Release` → framework copy → `pod install` (119 dependencies,
120 pods), exit 0, ending with `git status --porcelain` empty.

## Open blockers, in the order they block

### 1. Nothing — the bundle builds, and `.visionos.*` files now win

Two separate bugs, both fixed, both worth keeping written down.

**The bundle could not be built at all**, and the command everyone reached for
was the wrong one. `expo export --platform visionos` is rejected outright
(`Unsupported platform "visionos"`), and `expo export:embed --platform visionos`
dies in `getSupportPackageForPlatform` before touching app code. Neither is what
the app uses. The fork reports itself as iOS —
`@reactvision/react-native-visionos/React/Base/RCTConstants.m:10` sets
`RCTPlatformName = @"ios"` — and carries visionOS as a resolver *option*:
`RCTBundleURLProvider.mm:471` appends `resolver.platformExtension=visionos`
under `#if TARGET_OS_VISION`, and `scripts/react-native-xcode.sh:158-160` does
the same for release. The real command is:

```
cd apps/mobile
MOYO_VISIONOS_BUILD=1 node \
  ../../node_modules/@reactvision/react-native-visionos/cli.js bundle \
  --platform ios --resolver-option "platformExtension=visionos" --dev false \
  --entry-file /abs/path/to/node_modules/expo-router/entry.js \
  --bundle-output out.jsbundle --assets-dest out-assets
```

(The entry file must be an absolute path; a relative one resolves against the
wrong root and fails with `The resource /Users/node_modules/... was not found`.)

It failed on `Unable to resolve module react-native/setup-env`. Root cause is a
version skew, not a fork packaging bug: `react-native/setup-env` and
`react-native/asset-registry` were added in 0.87/0.88, the fork is on the 0.86
line (package 0.86.4, `reactNativeUpstreamVersion` 0.86.3), and upstream
`react-native@0.86.3` has no such `exports` keys either. `@expo/metro-runtime`
targets 0.88 and imports a name the 0.86 tree never had.

Both are now redirected **into** the fork at their 0.86 names
(`Libraries/Core/InitializeCore`, `Libraries/Image/AssetRegistry`), not excluded
from the rewrite. Excluding them would have resolved — the 0.88 files are on
disk — and bought the bundle a second React Native environment and a second
asset registry against a binary linking the fork's native runtime. A registry
the native side does not read returns `undefined` from `getAssetByID` for every
image: blank images, no error. `asset-registry` would have been the next
failure regardless, since `@expo/metro-config` puts that literal specifier in
`transformer.assetRegistryPath`.

**`.visionos.*` files did not resolve.** Nothing in `metro/src` or
`metro-resolver/src` reads `platformExtension`, and Expo's
`constructPlatformExtensions` keys off `platform`. Since the runtime asks for
`platform=ios`, Metro picked `hearts-gpu.tsx` and `KeyboardProvider.tsx` — both
of which import a module visionOS does not autolink. **Every `.visionos.tsx` in
this repo was dead code**, and the WebGPU splash fix committed in `5be01ec6` did
nothing. The resolver now swaps in a `visionos` → `ios` → `native` → bare
extension list on the visionOS path, mirroring `PLATFORM_EXTENSIONS` in
`@expo/config/build/paths/extensions.js`.

Verified against the real bundle's sourcemap, 8,669 sources:

```
react-native-webgpu:               17   (lazy chains only)
react-native-keyboard-controller:  61
visionos variants resolved:        components/KeyboardProvider.visionos.tsx
                                   components/splash/hearts-gpu.visionos.tsx
hearts-gpu:                        hearts-gpu.visionos.tsx        (.tsx absent)
KeyboardProvider:                  KeyboardProvider.visionos.tsx  (.tsx absent)
bare node_modules/react-native/:   0
```

The 17 WebGPU modules reach the graph only through `React.lazy` /
`await import()` in `tutor-avatar-3d.native.tsx` and `webgpu-smoke.tsx`, on
routes reachable only by `moyo://` deep link. In the graph, never evaluated.
The 61 keyboard-controller modules are safe for a different reason:
`specs/NativeKeyboardController.js` uses `TurboModuleRegistry.get`, which
returns null, not `getEnforcing`, which throws. There is no `getEnforcing` in

A plain `--platform ios` bundle still builds; the change is confined to the
`visionOS &&` branch.

### 3. The Apple Rive → Viro path

The prior handoff described this as an ABI defect. The audit found something
different and larger. All of the below is read-only fact with file:line
evidence; none of it is speculation.

**The overrun is not real on 64-bit.** Record layouts dumped with
`clang++ -Xclang -fdump-record-layouts`:

| target | `VROSharedTextureHandle` | `SharedHandlePayload` |
|---|---|---|
| `arm64-apple-ios` | 40 | 40 |
| `aarch64-linux-android` | 40 | 40 |
| `armv7a-linux-androideabi` | 24 | **28** |

On arm64 `fenceFd` lands exactly in the consumer struct's tail padding at
offsets 36–39, so the copy fits. What you get is a **silent dropped fence** —
the consumer reads it as padding, never waits, and the GPU read races the
producer write. Tearing, not corruption, which is harder to notice. On
`armeabi-v7a` it is a genuine 4-byte overrun, and 32-bit is in the ABI list in
`nitro-canvas-in-Vision/android/build.gradle:14`,
`virocore/android/sharedCode/build.gradle:26` and
`nitro-canvas-in-Vision/example-app/android/gradle.properties:31`.

**None of it is reachable today.** `VROExternalSurfaceTextureRegistry.{h,cpp}`
do not exist in `/Users/mikevocalz/virocore`; nothing calls
`nitro_canvas_lookup`; `VROExternalSurfaceTexture::updateFromHandle` has no
in-tree caller. The boundary wakes up only when two unapplied patches land, and
they are not independent — `-untracked` adds the caller, `-tracked` adds
`fenceFd`. **Applying `-untracked` alone reproduces both bugs.**

Three of those patches no longer apply to `pico-support`: `VROMaterial.h`
(tree `0e8dd40b` vs patch pre-image `104be2ef`), `capi/Material_JNI.cpp`
(`c3d479a0` vs `567acaf8`), `android/.../VROExternalSurfaceTextureImpl.cpp`
(`8727d9df` vs `82f333d8`).

**The Apple consumer does not exist at all.** Not "missing `importHandle`" —
`VROExternalSurfaceTexture.cpp` is not in the Apple build:
`grep -c "VROExternalSurfaceTexture" virocore/ios/ViroRenderer.xcodeproj/project.pbxproj`
returns `0`, while `android/sharedCode/CMakeLists.txt:291` compiles it. What is
needed is `virocore/ios/ViroKit/VROExternalSurfaceTextureImpl.mm` — the exact
path a comment at `VROExternalSurfaceTexture.cpp:10` already names — returning
`VROTextureSubstrateMetal`, modelled on the existing `VROVideoTextureCacheMetal`,
plus Sources-phase entries in **both** the ViroKit-iOS and ViroKit-visionOS
targets (mirroring how `VRODriverVisionOS.mm` is listed twice, pbxproj `:68`
and `:1093`).

On the producer side `nitro-canvas-in-Vision/ios/HybridCanvasSurface.swift:109-116`
shows `signalFrameReady` is still an M2 stub that discards `syncFd`, so there is
no Apple fence either.

The agreed fix is one vendored C header — `NitroCanvasSharedTextureABI.h`, owned
by `nitro-canvas-in-Vision/cpp/`, copied byte-identical to
`virocore/ViroRenderer/` — with `structSize` and `abiVersion` fields, all
fixed-width (no `bool`, no `uintptr_t`), 48 bytes with identical offsets across
armv7a, arm64-android, arm64-ios and i386. The lookup symbol gets
version-suffixed (`nitro_canvas_lookup_v2`) so a stale peer fails `dlsym` and
the panel renders blank rather than writing a mismatched struct. Since virocore
must stay dlsym-only, a copied header plus a runtime size check is the only
design that holds — no codegen, no build coupling.

**That header is now written, adopted on both sides, and committed:**
`nitro-canvas-in-Vision` `85372af` on `decax9-three-panel`, `virocore`
`8ee071b5` on `pico-support`. Neither is pushed.

`-fdump-record-layouts` gives byte-identical dumps on all four targets —
`armv7a-linux-androideabi`, `aarch64-linux-android`, `arm64-apple-ios` and
`arm64-apple-xros` — at `[sizeof=48, dsize=48, align=8]` with `fenceFd` at
offset 40. The producer compiles under `-Wall -Wextra` with zero diagnostics on
three targets, `llvm-nm` shows `nitro_canvas_lookup_v2` as the only exported
entry point (v1 was deleted, not kept alongside — it had no callers left), and
a host harness poisoning the caller's struct with `0xAB` confirms the guard
writes nothing when `structSize` or `abiVersion` disagree.

One thing the plan got wrong: there are **no `handle.sRGB` reads in virocore**
to convert. The only `sRGB` hits are the struct field itself and
`VROExternalSurfaceTexture::_sRGB`, an unrelated class member from its own
constructor.

**Required follow-up before that path lights up.**
`patches/virocore-v2.55.0-nitro-canvas-untracked.patch` still targets the
deleted symbol, so applying it as-is gets a `dlsym` miss and a permanently
blank panel. That is the designed fail-safe, not a fix. Three edits:

- `:55` — `dlsym(handle, "nitro_canvas_lookup")` → `"nitro_canvas_lookup_v2"`
- `:139-141` — `LookupFn = bool (*)(int, VROSharedTextureHandle *)` →
  `NitroCanvasLookupFn` from the shared header
- `:100-102` — set `handle.structSize = sizeof(handle)` and
  `handle.abiVersion = NITRO_CANVAS_ABI_VERSION` before the call, or the guard
  refuses every frame

## Standing traps for the next session

- **Do not run `pod install` while an `xcodebuild` is running** against the same
  workspace. It rewrites `Pods/Headers/Public` and the build fails on a missing
  modulemap that exists moments later. That is what happened here.
- The visionOS simulator **runtime** is not installed, only the SDK. A green
  build is not a launch.
- Recovering a dirty `.cache/visionos` costs a full ViroKit rebuild (~12 min); a
  fresh checkout rewrites every mtime regardless, so preserving `ios/build`
  would not help.
- `pod install` emits `[!] [Expo-precompiled] Failed to read spm.config.json ...
  undefined method 'filter_map'` for about a dozen modules. Non-fatal,
  pre-existing, a Ruby-version mismatch in Expo's CocoaPods scripts.
