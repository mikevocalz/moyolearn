# Moyo adult inquiries → SignalIQ

SOT: `packages/app/marketing/` · `packages/app/core/protected-operation.ts` · `packages/payload/src/marketing/endpoints.ts` · `packages/payload/migrations/signaliq_marketing_additive.sql` · `packages/auth/src/billing-payment.ts`

## What enters the connection

The public form on `/for-schools#request-demo` saves an adult's request in Moyo's own sales inbox. `/contact` links to that form. The visitor must affirm adulthood and permission for Moyo to answer. Sharing the inquiry and its business follow-ups with SignalIQ is a separate optional choice, initially off. No student field, learning history, household export, session transcript or freeform message is accepted.

This is Moyo's platform sales intake. A tutoring business's existing `families`, `leads`, enrollments and sessions belong to that customer's tenant. Those records are not a platform marketing prospect list and are not copied into Moyo's SignalIQ workspace.

| Actual Moyo source                                                   | SignalIQ fact                                                        | Limitation                                                                                                                                                     |
| -------------------------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Consented adult website inquiry                                      | Known contact inquiry; explicit school/business organization context | Organization is submitted and unverified. Email domain never proves employment. Family inquiries have no company.                                              |
| Moyo owner records a discovery-call appointment                      | Booking event linked to the original inquiry                         | This saves a business appointment record. It does not send a calendar invitation or claim a tutoring session occurred.                                         |
| Moyo owner records contacted, pilot started, proposal sent or closed | Business progress linked to the inquiry                              | These are owner attestations. They are not student progress or automatic proof of a sale.                                                                      |
| Better Auth's signature-verified Stripe `invoice.paid` callback      | Paid subscription invoice amount/currency and time                   | Requires an explicit link to a real organization or verified adult billing reference. A client cannot submit payment events.                                   |
| Owner withdraws inquiry and sharing                                  | Source-scoped consent suppression                                    | Stops queued payloads and suppresses processing in SignalIQ, including an inquiry whose prior delivery response was lost. This is not a full data-erasure API. |

SignalIQ source configuration determines the destination pipeline and which booking/order meanings move a deal's stage. New company and deal population requires that server-side source grant; a website analytics key cannot supply it. The browser tracker in PR152 remains separate: consented anonymous visits on `/for-schools` do not identify a person or imply a booked call.

## Source identifiers and truthful delivery state

`moyo.inquiry:<inquiry UUID>` is the stable inquiry source ID. A persisted `prospect_id` is reused only when adult email, audience, submitted organization name and submitted domain exactly match; new repeat inquiries do not invent a conflicting company. Each queued projection stays frozen, so a retry never changes its original hash. Booking/progress use the persisted update request UUID. Paid invoices use `moyo.invoice:<Stripe invoice ID>`. Every descendant carries the original `inquirySourceId`. `sourceRef` is a bounded internal `record:<UUID>`, without email or student data.

The inquiry and outbox insert commit together. Repeating the exact request ID and payload returns the same saved inquiry. Reusing that ID with changed fields is a conflict. Recording business progress is likewise idempotent. A timeout preserves the same source ID and payload for retry.

The outbox distinguishes:

- `pending`: no confirmed remote acceptance yet.
- `accepted`: SignalIQ saved the event, but downstream processing remains queued.
- `delivered`: SignalIQ returned `processed`, or acknowledged the specific withdrawal request.
- `blocked`: configuration, authorization, consent or source processing needs attention.
- `failed`: delivery retries were exhausted or a stored payload is invalid.

The sender polls the private receipt endpoint for accepted events. A queued receipt is never labeled delivered. Booking and payment events wait until their parent inquiry has a processed receipt. Withdrawal bypasses that dependency so it can create a remote tombstone even before an inquiry arrives. Row locks serialize sending with withdrawal; delivered or withdrawn outbox payloads no longer retain the adult contact fields. Failed consent suppression remains visible and can be retried.

## Internal Moyo sales workflow

Open `/admin/moyo-inquiries` on `admin.moyolearn.com`. This view extends the existing Payload admin; the navigation link appears only for the configured internal account IDs. Same-origin `/payload-api/moyo-sales/inquiries` handlers use Payload's verified session, require the authenticated collection to be `users`, and match the exact user ID against `MOYO_MARKETING_ADMIN_IDS`. A missing allowlist denies everyone. The user table has no trusted role column or mandatory email verification, so an email string does not grant access. Request bodies cannot select an actor or scope. Mutations also require the exact admin Origin; both reads and writes require the configured admin host.

This follows the account model in doc 06: founder/support identities belong to Payload's internal back office. Moyo's own marketing records are partitioned under the fixed `moyo-platform-sales` source scope, not a Better Auth customer organization. No customer organization, role or subscription is created, and existing paid customer operations keep their existing authorization gates. The internal account ID is recorded on every business update as `payload:<id>`. Shared Users update/delete access also protects every configured ID: other internal staff cannot change that identity’s credentials, and deletion requires first removing its server-owned binding. Configure the same IDs on every backend serving Payload Users so another API host cannot bypass this protection.

The inbox shows the latest 100 adult requests, sharing choice, delivery counts, safe error codes and last confirmed delivery. Its appointment is the most recently recorded booking, ordered by creation time and then update ID; rescheduling to an earlier date replaces the previous appointment, and recording business progress leaves the appointment intact. It supports recording a discovery call through Payload's date/time picker, business progress, explicitly linking an actual subscription and retrying recoverable delivery failures after source setup is fixed. Queued receipts remain unconfirmed. An explicit retry reposts the same source ID and exact payload so SignalIQ can revalidate and requeue a recoverable processing failure; permanent suppression and consent withdrawal cannot be overridden. Withdrawal remains available to the authorized internal administrator and can retry failed consent suppression.

Link billing with the actual Better Auth subscription `referenceId`. For an organization, that ID must exist in the canonical organization table. For an individual, the account email must match the inquiry and be verified; managed learner and minor accounts are refused. A Stripe customer ID supplied by a browser is never trusted. One customer can link to only one inquiry in the Moyo internal sales source.

The verified webhook persists a minimal local receipt: invoice ID, customer and subscription IDs, paid amount/currency/time, live/test flag and evidence status. The deployed Stripe endpoint uses API `2026-08-26.dahlia`; its current `parent.subscription_details` and each line’s `pricing.price_details.price` provide the explicit subscription/price facts. An invoice proves Moyo revenue only when its entire line set is present, every line has a configured Moyo plan price and the same subscription, and the exact subscription/customer pair belongs to the canonical Better Auth reference explicitly linked to this inquiry. A shared Stripe customer alone cannot attribute another product or another reference’s invoice. One-off invoices have no supported subscription attribution. The journal's `amount_cents` field retains the original integer Stripe `amount_paid` representation and must fit its actual PostgreSQL integer column.

Signal order outcomes use ISO minor units. Only the projection converts Stripe's documented representation exceptions: ISK and UGX divide by 100 exactly; MGA multiplies by 100. USD, JPY, three-decimal currencies, and the invoice charge amounts for HUF/TWD keep their original integer units. HUF/TWD's payout restrictions do not apply to paid invoices. This changes denomination only, never currency, exchange rate or monetary value. Fractional results and converted values above 2,147,483,647 stay private with `invoice_amount_unrepresentable` and appear in billing review; no order is emitted. The final delivery check and repeat migration compare the same exact conversion. Earlier incompatible frozen orders are quarantined, never silently rewritten under their original source ID. Raw journal amount/currency/time and immutable repair comparisons remain unchanged. See [Stripe's currency units and special cases](https://docs.stripe.com/currencies) and the [SIX ISO 4217 current currency list](https://www.six-group.com/dam/download/financial-information/data-center/iso-currrency/lists/list-one.xml) (publication 2026-09-17). General ISO outcome formatting must use explicit storage exponents: an Intl/CLDR display default can differ from the currency's ISO minor units. SignalIQ's native Stripe ledger retains its separate provider units.

Valid configured-price receipts are saved before the canonical subscription or inquiry link exists. The private worker reconciles them again each run, so `invoice.paid` arriving before `subscription.created` does not require another form submission or operator relink. Incomplete or mixed evidence remains unexported. Linked receipts needing review and valid receipts waiting for their exact subscription association appear separately in the inbox. The private worker can re-read one unresolved invoice, then at most 100 lines if the embedded list was incomplete, using the existing billing key. Each Stripe request has a three-second timeout and no SDK retries; incomplete lists, mixed prices and read-permission failures remain visible. Automatic evidence rechecks back off for 30 minutes; the internal operator can request another verification after correcting the source. No permission grant or key rotation is performed by this code.

Only a consented, active inquiry with complete price proof and the exact canonical association yields an order. The sender revalidates retained orders immediately before export. Migration quarantines legacy unproven pending/accepted orders; old receipts without subscription/price evidence do not become valid by customer matching. Replays cannot rewrite the original amount, currency, subscription, customer or paid time. Raw invoice bodies, customer addresses, line items and payment credentials are never retained in the connection. Test-mode invoices do not enter production. Historical invoices predating this connection are not fabricated or silently backfilled, and actual dates are never rewritten to bypass SignalIQ’s 30-day intake window.

## Deployment contract

There are three applications. The Vite marketing app serves the form; the Next app serves public intake, the verified Stripe callback and the private outbox worker; admin-vite serves the existing Payload session, new internal inbox and internal update endpoints. Deploy the schema and both backends first, then the marketing form. Verify each production SHA independently.

The shared domain lives in `@acme/app/marketing`. Its service owns operations and calls its repository for database access; Payload endpoints and Next routes consume the public domain entry. Pure schemas and transport contracts have separate exports and import no database runtime. The Payload package depends on the app domain, and the app domain does not import Payload. Shared service and repository files begin with the literal `import 'server-only'` required by the common lint rule. Next retains that marker. The admin compiler narrowly translates it within the shared sales domain and common operation module to TanStack's native marker, preserving the compiler's client-import rejection; it does not alias the marker to an empty module. Admin import protection also rejects both the public server entry and direct service, repository, permission and operation imports. Only pure contract exports enter the admin client bundle.

Every service entry runs through the same `protectedOperation` engine and its `finally` telemetry. Closed source modes derive an internal context from the authenticated Payload request, an anonymous context from the public intake guard, or a machine context from the private cron credential or already signature-verified billing callback. They never create a Better Auth customer, organization or subscription and never enter the development session-mock branch. Customer operations retain their session, host, role and entitlement gates. Denied attempts also produce a standard operation record containing only fixed operation names, context kind, outcome and timing; headers, body fields, actor IDs, source IDs and payment facts are excluded.

Server-only settings. The internal-ID setting belongs to both `moyo-admin` and `moyo-app`, because both serve the shared Payload Users API. The admin-origin setting belongs to `moyo-admin`; sender, rate-limit, cron and billing settings belong to `moyo-app`. Both use the existing canonical database:

| Setting                                                                | Meaning                                                                                                              |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`                                                         | Existing canonical Moyo database connection; never export it to client variables.                                    |
| `MOYO_MARKETING_ADMIN_IDS`                                             | Exact verified internal Payload account IDs, comma-separated; required on both backends, default deny for the inbox. |
| `MOYO_MARKETING_ADMIN_ORIGIN`                                          | Exact HTTPS internal admin origin; default `https://admin.moyolearn.com`.                                            |
| `MOYO_MARKETING_ALLOWED_ORIGINS`                                       | Exact HTTPS form origins, comma-separated; default `https://www.moyolearn.com`.                                      |
| `MOYO_MARKETING_RATE_SECRET`                                           | Random private HMAC key for hourly request limiting. Raw IP addresses are not retained.                              |
| `SIGNALIQ_BUSINESS_ENDPOINT`                                           | Exact HTTPS `/api/ingest/v1/business-events` endpoint.                                                               |
| `SIGNALIQ_BUSINESS_KEY`                                                | Private `write_server` credential for the approved Moyo source. Never use a `VITE_`/`NEXT_PUBLIC_` variable.         |
| `CRON_SECRET`                                                          | Existing private Vercel cron credential.                                                                             |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, existing price variables | Existing Better Auth billing setup; its live endpoint must include `invoice.paid`.                                   |

`apps/web/vercel.json` schedules `/api/marketing/sync` once per minute. Confirm the deployed Vercel plan accepts this schedule. The handler forwards the original request to the service's common operation boundary, whose closed cron mode checks `CRON_SECRET` before any drain work. Each run is bounded to three deliveries, waits at most six seconds per SignalIQ request and backs off failures. A run may also perform the bounded invoice evidence recheck described above. No public route can manually drain the queue. If a deployment's plan cannot run this cadence, use an authorized existing scheduler against the same private handler; do not claim minute delivery or silently upgrade a paid plan.

After an authenticated drain, the handler writes one structured `moyo.marketing.sync` log with the returned state and aggregate processed count. Failure writes only that event name and `state: "failed"`; it never includes the exception, credential, request body, contact or invoice/customer identifiers. Unauthorized requests produce no drain receipt. A successful `processed: 0` proves the authenticated worker route ran, not that any customer record was delivered. Use provider timestamps on these receipts to verify actual scheduling after deployment.

The intake checks exact Origin, JSON content type, an 8 KiB body ceiling, strict schema and five new requests per hashed address per hour. Duplicate exact requests do not spend another limit. CORS does not grant reads. The endpoint always chooses the fixed internal sales scope from server code. Missing configuration fails visibly rather than reporting a saved inquiry. The form preserves entered values after failure and reuses its request ID on retry.

## Reviewed release commands

Run these inside the existing Next deployment environment. Credentials remain in that environment, not in logs or an exported env file:

```sh
node --import tsx apps/web/scripts/marketing-migrate.mts --preflight
node --import tsx apps/web/scripts/marketing-migrate.mts --billing-preflight
node --import tsx apps/web/scripts/marketing-migrate.mts --apply
```

If the working directory is `apps/web`, use `scripts/marketing-migrate.mts` instead. `--preflight` requires `MOYO_MARKETING_OWNER_EMAIL` and reads only that exact account: legacy Better Auth organization/entitlement diagnostics and the matching internal Payload account ID/role. Missing customer organizations do not block internal sales administration. It changes nothing. `--billing-preflight` independently reads the authenticated Stripe account ID, webhook configuration matching the exact Moyo app endpoint, and one configured OPS price ID/currency/live flag. A failed step reports only sanitized Stripe error type/status/code and does not hide other successful reads. It changes nothing and prints no customer, invoice or credential data. The catalog deliberately stores environment price IDs rather than a hardcoded currency; source pipeline currency must match this actual configured price.

`--apply` executes the committed additive SQL in one transaction with a schema lock. It creates five restricted tables and can be repeated. RLS is enabled; PUBLIC and existing Supabase `anon`/`authenticated` table grants are revoked. Only the existing trusted database server role may operate them. The script does not create users, organizations, memberships, subscriptions or customer records. A production deployment is not verified until the schema, exact internal account authorization, private source grant, billing endpoint and actual scheduler have all been checked.

The database suite applies the actual Better Auth schema and additive marketing migration, exercises concurrent idempotency, internal session/account-ID/host/origin gates and fixed source isolation, earlier-date rescheduling with deterministic booking ordering and progress isolation, queue receipts, timeout then withdrawal, in-flight withdrawal serialization, repeat-prospect stability, exact recoverable replay, reviewed release preflight, verified invoice linking, late canonical subscription recovery, shared-customer/reference isolation, incomplete/mixed evidence repair, immutable receipt facts, legacy-order quarantine, input limits and public database grants.
