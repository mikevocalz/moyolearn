# ADR desktop/0001: Spark app in an isolated workspace

- Status: Accepted (PR-D01)
- Date: 2026-11-04
- Supersedes: draft PR #137 (`feat/moyo-legend-spark-desktop-preview`)
- SOT-KEYWORDS: desktop adr spark workspace isolation expo-sdk nitro lockfile

## Context

Moyo Learn mobile and web run Expo SDK 58, React Native 0.88 and Nitro
`1.0.0-alpha.nightly.100.g107f6fc66597` from one pnpm workspace (`apps/*`,
`packages/*`) with root `pnpm.overrides`.

Legend Spark 0.0.2 is the npm `latest` release on 2026-11-04. The `next` tag
resolves to 0.0.1-next.10, which is older (SDK 54 / RN 0.81). Spark 0.0.2 pins,
read from the generated app and `node_modules` after `spark create`:

| Package | Version |
| --- | --- |
| `@legendapp/spark` | 0.0.2 |
| `expo` | 55.0.32 |
| `react-native` | 0.83.10 |
| `react-native-macos` | 0.83.0 |
| `expo-desktop` | 1.0.6 |
| `react-native-nitro-modules` | 0.37.0, from `spark-packages/react-native-nitro-modules-5df87747….tgz` |

`spark doctor` requires `react`, `react-native`, `expo` and
`react-native-macos` to match those pins exactly, including in overrides. The
root overrides set SDK 58 values for the same names. Nitro 0.37.0 and the v1
nightly cannot live in one graph: `react-native-nitro-modules` throws
"Nitro was installed twice" when the native and JS versions differ
(`src/turbomodule/NativeNitroModules.ts`).

Spark also needs its `postinstall` (`node node_modules/@legendapp/spark/init-template.cjs`),
which prepares the patched native inputs under `spark-packages/`. Draft #137
had a contract test that forbade that script and an override that pulled stock
Nitro 0.37.0 instead of Spark's AppKit-patched tarball.

## Decision

1. `apps/desktop` is a standalone npm project generated by
   `spark create MoyoLearn --platform macos --bundle-id com.moyolearn.desktop --package-manager npm`.
   It keeps the creator's `package.json` pins, `overrides`, `spark-packages/`
   tarballs and `package-lock.json`. npm, not pnpm, so that no pnpm process
   walking up to the root `pnpm-workspace.yaml` can adopt it.
2. The root `pnpm-workspace.yaml` excludes it with `"!apps/desktop"`.
   `pnpm -r ls` with pnpm 10.32.1 confirms the exclusion.
3. The postinstall stays. CI runs `npm ci` with scripts enabled.
4. Shared code crosses the boundary as source files, not packages. D01 imports
   one file, `packages/theme/tokens.ts`, by relative path; it has no imports.
   Metro watches `packages/theme` through `watchFolders`. A `file:` dependency
   on `@acme/theme` was rejected because npm would read its `workspace:*` and
   `catalog:` specs.
5. `@acme/ui` stays out of desktop (DEFER). It reaches Nitro v1, `@expo/ui`,
   `expo-router` and Viro across 37 non-story files (count from
   `docs/decisions/2026-11-04-open-pr-dispositions.md`). Desktop controls come from
   `@legendapp/spark/ui`; message dialogs come from `@legendapp/spark/dialogs`.
6. `.github/workflows/desktop.yml` guards the split: a `root-isolation` job runs
   `apps/desktop/scripts/check-root-isolation.mjs` against the committed
   `pnpm-workspace.yaml` and `pnpm-lock.yaml`.

## Re-evaluation trigger

Re-include `apps/desktop` in the root workspace when a Spark release on the
channel this app was created on (`latest`) pins Expo SDK 58 or later and a
Nitro build the root can share. Check with `npx --no-install spark upgrade --dry-run`
inside `apps/desktop`. Until then, every shared package the desktop imports
must compile under both Expo pins or expose a `desktop` condition in `exports`.

## Consequences

- Two lockfiles. Desktop dependency bumps go through `spark upgrade`, never
  through the root npm-latest refresh.
- The root `business-studio-npm.mjs` gate globs `apps/*/package.json`. It only
  checks its own target list (gesture handler, Reanimated, Worklets, Skia,
  WebGPU, TypeGPU), none of which `apps/desktop` declares. This was read, not run.
- Desktop UI cannot reuse `@acme/ui` components until a desktop-safe subpath
  exists. Tokens are shared; components are not.
- `zustand` is 5.0.16 in desktop and 5.0.15 in the root catalog. The root
  catalog moves with the next npm-latest refresh.

## Known upstream defect carried in this decision

With `expo.experiments.outOfTreePlatforms: true` (the Spark template default),
Expo CLI turns on autolinking module resolution and loads every dependency's
`react-native.config.js`. `react-native-windows@0.83.2`'s config requires
`@react-native-windows/cli`, whose `lib-commonjs/utils/commandWithProgress.js`
calls `findPowerShell()` at module load. The hoisted
`@react-native-windows/find-dotnet-tools@0.0.0-canary.3` (a Spark dependency)
throws "Unable to find pwsh.exe" on macOS. `spark analyze` and `spark build`
fail on an untouched 0.0.2 template the same way.

`desktop.config.json` sets `expo.experiments.autolinkingModuleResolution: false`.
With it, `spark analyze` exits 0 on both the template and this app. The cost is
losing Expo's sticky resolution of duplicate native packages, which matters in
monorepo installs and not in this single-package npm graph. Remove the flag
once a Spark release fixes the load order, and report the defect upstream.
