## Final store contract

```ts
type WorksheetSyncStatus = 'idle' | 'syncing' | 'confirmed' | 'pending' | 'reconciled' | 'error';
type AdvanceOutcomeInput = Omit<AdvanceInput, 'fromQuestionId' | 'expectedIndex'>;

interface WorksheetCacheRecord {            // homework-submission-v2:<encodeURIComponent(learnerAuthId)>
  readonly schemaVersion: 2;
  readonly learnerAuthId: string;
  readonly confirmed: HomeworkSubmissionView;
  readonly pending: readonly AdvanceInput[];
}

interface WorksheetState {
  current: HomeworkSubmissionView | null;   // confirmed + pending replayed
  ownerId: string | null;
  pending: readonly AdvanceInput[];
  status: WorksheetSyncStatus;
  restore(learnerAuthId: string): HomeworkSubmissionView | null;
  hydrate(learnerAuthId: string, submissionId?: string): Promise<HomeworkSubmissionView | null>;
  begin(learnerAuthId: string, input: CreateSubmissionInput): Promise<HomeworkSubmissionView>;
  start(tutorSessionId: string): Promise<void>;
  advance(input: AdvanceOutcomeInput): Promise<WorksheetSyncStatus>;
  revise(questionId: string, input: ReviseQuestionInput): Promise<HomeworkQuestionView>;
  clear(learnerAuthId: string): void;
}
```

Behaviour per call:

- `advance` fills `fromQuestionId`/`expectedIndex` from the replayed cursor, so a caller cannot send a stale index by hand. It appends to `pending` and writes storage before the first `await`, so the screen moves in the same tick. One flush per learner at a time. Outcomes: success shifts the move into `confirmed` (`confirmed` when the list empties); `StaleCursorError` adopts `current`, drops every pending move (each assumed the old cursor), then refetches the view, status `reconciled`; a retryable failure keeps the moves, status `pending`; a settled refusal (400/403/404) keeps them too, status `error`, shown on screen.
- `hydrate` restores, migrates v1 if there is no v2 record, flushes, and reads the server view only when nothing is pending. A 404 deletes the cache.
- `begin` is idempotent on `submissionId`; the capture screen reuses one id across retries.
- Past the last question the store mirrors the repository: cursor stays, `status: 'complete'`, and `advance` becomes a no-op.

## Decisions a reviewer should check

1. `begin` and `hydrate` take `learnerAuthId` explicitly. The brief's `begin(input)` would have keyed storage on `view.learnerAuthId`; the tutor screen keys on `activeContext.learnerId ?? user.id`, and I could not verify the two are always the same string, so the key is whatever the screen passes.
2. Linking the tutor session happens in `tutor-screen.tsx`, not `capture-screen.tsx`. The capture screen navigates away before the tutor store has a `sessionId`; the tutor screen sees both.
3. Skip is derived: leaving a question with zero learner turns since its bubble and zero hints records `skipped`. No separate skip button was added. `attempts` is the learner-turn count since the bubble. `solved-independently` needs `lastOutcome === 'correct'` with zero hints; photographed pages never call `/api/tutor/evaluate`, so worksheets never record it.
4. v1 migration creates the submission from the v1 record (`submissionId = v1.id`) and replays the v1 cursor as moves with outcome `unresolved`, since v1 stored no outcomes. While offline the v1 key stays and the tutor screen shows no question bar for that worksheet until the create lands.
5. Crops go up as `null`. `CapturePage` carries no storage key or pixel size, and the upload queue's `CompletedUpload.storageKey` is not reported back to the capture screen. Wiring it needs a change in `features/media`, outside my paths.
6. `revise` has no UI caller yet; review edits happen before the submission exists.
