## Decisions a reviewer should check

1. **Evidence is issued in the service, not the repository.** The brief put `issueEduQuestion` inside `reviseQuestion`. It moved to `homework.service.ts:evidenceFor` so `evaluationReady: false` is a literal the fake-port test can assert. Create issues evidence too (contract: "confirming a question issues"), once, on the first attempt only. Order is persist, then issue. If the issue fails, the edu row lags, the quoted revision does not match, and the evaluator refuses. Both orders fail closed.
2. **Evidence is bound to the child.** `issueEduQuestion` writes `ctx.learnerId` as `learner_id`. `issueHomeworkEvidence` passes a ctx naming the learner the service proved, so a guardian's confirmation lands under the ward. This is the one place a ctx is built in a repository; it is commented.
3. **`advance` takes a row lock.** `beginTransaction` alone does not serialise two devices under READ COMMITTED: both can read index 2 and both write 3. `advanceSubmission` runs `select … for update` through `payload.db.sessions[transactionID].db.execute` before the compare. That reaches into the drizzle adapter's `sessions` map, typed by a local cast (`DrizzleSessions`), not by a public Payload API. If the canary renames it, `advance` throws, and nothing writes.
4. **By-id reads answer 403 for another family's id, 404 for an unknown one.** This follows the brief's ward rule. It differs from `guardianSummaryReport`, which returns null for both so the id space is not an oracle. Submission ids are client-minted UUIDs, so the exposure is small, but it is a choice to confirm. A create with another learner's `submissionId` answers 409 `submission-conflict`, which has the same property.
5. **POST /submissions answers 201 on create, 200 on retry.** The contract names only the retry's 200.
